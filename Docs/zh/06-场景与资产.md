# 06 - 场景与资产

只改一个 JSON 文件就能让项目渲染一个 glTF 模型 —— 不写任何代码。本文说明怎么做、场景是怎么组织的、以及相机怎么操作。

## 最快路径

先拉取官方示例资产：

```powershell
./Scripts/FetchSampleAssets.ps1
```

这个脚本把 Khronos 的 `glTF-Sample-Assets` 浅克隆到仓库根目录的 `Assets/`（149 个模型，几个 GB）。`Assets/` 不纳入版本管理：绝大多数模型用不到，让每次克隆都付这个代价不合理。再次运行会走更新分支，`-Force` 重新克隆。

然后在项目的 `ProjectSettings.json` 里加一个 `scene` 分组：

```json
{
	"version": 1,
	"name": "MyViewer",
	"scene": {
		"gltf": "glTF-Sample-Assets/Models/DamagedHelmet/glTF-Binary/DamagedHelmet.glb"
	}
}
```

重新构建并运行，模型就出现在视口里。

仓库里的 `Projects/GltfViewer/` 就是这样一个项目：**没有任何 C++ 源码**，只有 `ProjectSettings.json` 和那个所有项目都一样的一行 `CMakeLists.txt`。

## scene 配置项

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `gltf` | `""` | 模型路径。空表示不加载场景，这是合法配置而非错误 |
| `cameraFieldOfView` | `60.0` | 垂直视场角，单位是度 |
| `cameraMoveSpeed` | `3.0` | 飞行相机的基础速度，单位每秒 |
| `lightIntensity` | `3.0` | 方向光强度。设为 0 则只剩环境光 |
| `ambientStrength` | `0.25` | 环境光。代替间接光照，没有它背光面会全黑 |

**路径解析顺序**：绝对路径直接使用；相对路径依次在项目目录、`Assets/` 目录、可执行文件目录下查找。项目目录优先，所以项目自带的模型会盖过示例资产里的同名文件。

**数值会被夹到合法区间而不是拒绝**。手改的配置文件里写了越界的数应该还能启动 —— 一个被静默纠正的值比拒绝运行更容易排查。

## 出错时会怎样

这条路径上每一步失败都不会让引擎起不来：

| 情况 | 行为 |
| --- | --- |
| `gltf` 为空 | 正常启动，空场景，**不告警**（这是正常配置） |
| 路径找不到 | 记录一条 error，继续跑空场景 |
| 文件解析失败 | 记录一条 error 并附上 tinygltf 的原因，继续跑空场景 |
| tinygltf 有 warning | 记录 warning，继续加载 |

错误只在启动时记录一次，**不在每帧的渲染里记** —— 否则日志会被刷爆。

## 加载是异步的

glTF 在后台线程解析，主线程每帧检查一次结果。所以窗口在大场景加载期间是可以操作的，视口中央会显示正在加载哪个文件、已经过了多少秒。

这样划分是因为两半的约束不同：解析产出纯数据、不碰引擎状态，可以在任意线程跑；把数据变成实体要写场景的 registry，必须留在读它的那个线程。实测 Bistro（420 万三角形、2.2 GB 贴图）解析约 15 秒、建实体约 0.9 秒，所以搬走解析就去掉了绝大部分停顿，剩下的短到一帧内做完即可。

对使用者的影响有两点：

- **启动后场景不是立刻就绪**。脚本要判断场景是否已加载，用 `scene.info` 的 `loading` 字段，不要 sleep 一个猜测的时长。
- **加载期间关窗口是安全的**。引擎会等那次导入结束再退出，因为工作线程正在往引擎的成员里写。

显示分三个阶段，因为三者能提供的信息不同：

| 阶段 | 显示 | 为什么 |
| --- | --- | --- |
| 解析 | 已耗时 | tinygltf 是单次调用，返回时才结束，拿不到中间进度 |
| 贴图 | 已完成 / 总数 + 进度条 | 循环由导入器自己控制，可以逐张计数 |
| 网格 | 已完成 / 总数 + 进度条 | 同上 |

不把三段合成一个总百分比：各阶段耗时占比随资产差别很大（Bistro 贴图占八成，纯几何模型几乎为零），合成就得给出一组权重，而那组权重只对测它的那个场景成立。

## 支持的 glTF 特性

| 特性 | 支持情况 |
| --- | --- |
| `.gltf` / `.glb` | 都支持。扩展名不符时会尝试另一种容器 |
| 节点层级 | 支持，父子变换按层级传播 |
| 节点变换 | TRS 与 4x4 矩阵都支持，矩阵会被分解成可编辑的 TRS |
| 网格 | 支持。一个网格的多个 primitive 按材质分段 |
| 顶点属性 | `POSITION`、`NORMAL`、`TEXCOORD_0` |
| 索引 | 8/16/32 位统一转成 32 位；无索引图元会生成索引 |
| 基础色 | `baseColorFactor` 与 `baseColorTexture`；也读 `KHR_materials_pbrSpecularGlossiness` 的 `diffuseFactor` / `diffuseTexture` |
| alpha 裁剪 | `MASK` 模式的 `alphaCutoff` |
| 缺少法线 | 按面法线生成并累加平滑 |
| 图像通道 | 1/2/3/4 通道统一展开为 RGBA |
| 图像格式 | PNG / JPEG 等经 stb 解码；**DDS 见下节** |
| 非三角图元 | 跳过该 primitive（不影响模型其余部分） |

## DDS 贴图

支持 `MSFT_texture_dds` 扩展与直接引用的 `.dds` 文件。压缩数据**不做 CPU 解码**，块数据原样上传给 GPU —— 一张 4096² 的 BC7 贴图在磁盘上 22 MB，进显存后仍是 22 MB；解成 RGBA 的话仅顶层就要 89 MB。

| 支持 | 说明 |
| --- | --- |
| 容器 | **仅 DX10 扩展头**（`DDS_HEADER_DXT10`） |
| 格式 | BC1–BC7（含各自的 sRGB 变体）、RGBA8 / BGRA8 |
| mipmap | 完整 mip 链，逐级上传 |
| 维度 | 仅 2D |

不支持的会**明确报错并说明怎么办**，而不是猜：

| 情况 | 行为 |
| --- | --- |
| legacy `DDS_PIXELFORMAT` 头 | 拒绝，提示用 `texconv -dx10` 或 NVIDIA Texture Tools 转换 |
| cubemap / 3D / 纹理数组 | 拒绝并说明是哪种 |
| 未映射的 DXGI 格式 | 拒绝并给出格式编号 |
| mip 链中途截断 | 保留已有层级（降级的贴图好过没有贴图） |

**为什么不支持 legacy 头**：那条路径用位掩码描述 D3D9 时代的格式，猜错会得到一张「看起来像但通道错位」的贴图 —— 这比直接失败难排查得多。而现代工具（texconv、NVIDIA Texture Tools、Compressonator）默认都写 DX10 头。

**单张贴图读不了不会拖垮整个场景**：记一条警告，该材质回退到白色贴图，其余照常加载。

> **为什么不引第三方库**：需要的只是「读懂头部、算出每层 mip 的偏移」，约 250 行。NVIDIA 自家的 Donut 框架（RTXDI 示例用它加载资产，同样基于 NVRHI）也是自己实现 `DDSFile.cpp`，其 `.gitmodules` 里没有任何 DDS 库 —— 它的文件头注释写明参考了 DirectXTK 的 `DDSTextureLoader` 而非依赖它。DirectXTex 虽然 DDS 部分不绑 D3D 设备（Vulkan 也能用），但要链 3 个 Windows 系统库、需要 COM 初始化，且官方非 Windows 支持仅限 WSL，对这点需求不划算。

**着色**是单个方向光下的 Blinn-Phong。glTF 基础规范不定义光源，所以场景构建时会自动补一个方向光。

**相机**根据模型的世界包围盒自动摆放，任意尺寸和位置的模型都不需要单独配置。

> 视线的初始方向是固定的：glTF 规范没有规定模型朝向，示例资产之间也不一致，所以没有可靠办法判断哪面是正面。想看别的角度，用飞行相机。

## 飞行相机

操作与 Unity 场景视图一致：

| 操作 | 效果 |
| --- | --- |
| 按住鼠标右键 | 进入飞行模式，光标隐藏 |
| 移动鼠标 | 控制视角朝向 |
| `W` / `S` | 前进 / 后退 |
| `A` / `D` | 左移 / 右移 |
| `Q` / `E` | 下降 / 上升（沿**世界**竖直轴） |
| 滚轮 | 调整移动速度 |
| `Shift` | 加速 |
| 松开右键 | 立即退出，交还光标 |

几个刻意的设计：

- **只有光标在视口内按下右键才会进入飞行**，所以右键点面板不会把视角抢走。但一旦飞起来，光标划过面板也不会被弹出 —— 拖拽横跨整个窗口是常规操作。
- **视角跟随鼠标是 1:1 的，不乘时间增量**。乘了会让 30fps 和 144fps 手感不同，同样的手部动作落在不同位置。
- **`Q`/`E` 沿世界竖直轴而非相机自身的上方向**。这样抬头时按 `E` 是纯上升，不会边升边往前飘。
- **滚轮调速是乘法而非加法**。固定增量在低速端太粗、高速端太细。
- **俯仰被夹在 ±89°**。正好 90° 时视线与世界上轴平行，视角会不可预测地翻滚。

## 场景是怎么组织的

场景采用实体组件方式（基于 EnTT）。组件都是纯数据，不含行为：

| 组件 | 内容 |
| --- | --- |
| `FNameComponent` | 名称。glTF 未命名的节点会得到 `Node <索引>` |
| `FTransformComponent` | 局部变换：平移、旋转（四元数）、缩放 |
| `FWorldTransformComponent` | 世界矩阵与法线矩阵，**每帧推导得出** |
| `FHierarchyComponent` | 父实体与子实体列表 |
| `FMeshRendererComponent` | 网格索引与可见性 |
| `FDirectionalLightComponent` | 方向、颜色、强度 |

两个值得说明的地方：

**局部变换与世界矩阵分开存储。** 世界矩阵只由 `FScene::UpdateTransforms` 从局部变换推导，不允许直接改。两份可独立修改的同一信息必然会不同步，表现出来就是「子节点突然不跟着父节点动了」。

**层级传播用显式栈迭代，不用递归。** 官方数据集里存在很深的节点树，深度由数据决定、编译期无法约束，递归会爆栈。

## 场景层级面板

编辑器左侧的 Scene Hierarchy 面板以树形展示场景：

- `[M]` 表示该节点有网格，`[L]` 表示是光源，`[ ]` 是纯分组节点
- 点击节点即选中，选中项高亮；Inspector 随即显示它的变换、世界位置与网格信息
- 顶部显示实体总数、网格数、三角形数
- 过滤框按名称筛选，**会保留通向匹配项的父节点** —— 否则匹配项会被过滤本身折叠的分支藏起来

> 面板停靠在左侧而非 Inspector 旁边。同一槽位的面板会变成 Tab，而只有被选中的 Tab 能被 hover 或点击 —— 放一起会让其中一个对 UI 自动化不可达。

## 自动化命令

| 命令 | 作用 |
| --- | --- |
| `scene.info` | 场景路径与实体、网格、三角形、材质、贴图数量；`loading` 表示后台导入是否仍在进行 |
| `scene.list` | 层级树，子节点嵌套返回 |
| `scene.camera.get` | 相机位置、朝向、视场、近远平面 |
| `scene.camera.set` | 设置相机位姿。参数 `position`、`yaw`、`pitch`（度），省略的字段保持不变 |
| `scene.select` | 按名称选中实体；省略 `name` 则清除选中 |

`scene.camera.set` 是让截图可复现的关键 —— 相机不固定，同一场景两次截图会因视角漂移而不同，逐字节比较就没有意义了。

```python
from lime_automation import LimeSession

sess = LimeSession(project="GltfViewer")
with sess as engine:
    info = engine.call("scene.info")
    print(f"{info['triangles']} 个三角形")

    # 固定相机后截图，保证可复现
    engine.call("scene.camera.set", position=[0.0, 0.0, -4.0], yaw=0.0, pitch=0.0)
    engine.wait_frames(5)
    first = engine.screenshot(source="viewport")

    engine.wait_frames(5)
    assert engine.screenshot(source="viewport") == first
```

> 截图前要等足够的帧数。改设置在下一帧生效，截图本身也要等一帧渲染完成，等太少会取到改动落地前的画面。

## 相关代码

| 位置 | 职责 |
| --- | --- |
| `Engine/Source/Runtime/Asset/` | glTF 导入，产出纯 CPU 数据，**不依赖 GPU** |
| `Engine/Source/Runtime/Scene/` | 实体组件场景、层级传播、GPU 资源上传 |
| `Engine/Source/Runtime/Camera/` | `ICamera` 基类、透视相机、飞行控制器 |
| `Engine/Source/Runtime/Renderer/Passes/` | `FBlinnPhongForwardPass` 与其着色器 |
| `Engine/Shaders/Passes/BlinnPhong.hlsl` | 着色器 |

`Asset` 模块刻意不依赖 GPU：glTF 解析、矩阵分解、层级展平因此都能在没有显卡的环境下用 Catch2 单测验证。

想加别的着色方式，按技术手段命名新建一个 Pass 放在 `Renderer/Passes/` 下 —— 现有的 `FBlinnPhongForwardPass` 就是这么命名的，延迟渲染或 PBR 路径是它的兄弟而不是替代品。
