# 创建项目

本文从零建立一个可运行的新项目，并解释引擎与项目的职责边界。

## 引擎与项目的关系

引擎接管 `main`。项目提供的是「内容」—— 渲染 Pass、编辑器面板、Shader、配置 —— 而不是程序框架。

具体来说，项目**不做**这几件事：

- 不写 `main` 或 `WinMain`
- 不在 CMake 里列源文件
- 不主动调用引擎去注册自己的 Pass 或 Panel
- 不管理窗口、设备、交换链、命令列表的生命周期

项目**只做**两件事：写类，然后用一个宏声明这个类存在。剩下的由引擎在启动时按顺序完成。

这个边界带来一个实际好处：项目代码里没有初始化顺序的坑。Pass 的 `Initialize` 被调用时，设备一定已经就绪。

## 目录结构

```
Projects/<项目名>/
  ProjectSettings.json  项目名、窗口、RHI、场景、自动化配置（唯一必需的文件）
  CMakeLists.txt        一行 lime_add_project()。有源码时才需要
  EditorSettings.json   编辑器外观（可选，缺省即用内置默认值）
  Source/               Pass 与 Panel 的 .h/.cpp，CMake 自动 glob（可选）
  Shaders/              HLSL 与一个 ShaderMake .cfg（可选）
  Automation/           Python 自动化脚本（可选）
  Content/              资产，构建后复制到可执行文件旁（可选）
```

目录名固定，引擎和 CMake 按这个约定查找。`Source/` 与 `Shaders/` 可以通过 `lime_add_project` 的参数改名，但没必要。

## 第一步：CMakeLists.txt

`Projects/CMakeLists.txt` 会自动扫描子目录，**只要目录里有 `CMakeLists.txt` 就会被加入构建**，所以不需要手动登记。

新建 `Projects/MyGame/CMakeLists.txt`，内容一行：

```cmake
lime_add_project()
```

就这一行。它会：

- 从 `ProjectSettings.json` 读 `name`，作为可执行文件名和 CMake 目标名
- glob `Source/` 下所有 `.cpp` 与 `.h`
- 把 `Shaders/*.cfg` 交给 ShaderMake，输出到 `Shaders/<项目名>/`
- 把 `ProjectSettings.json`、`EditorSettings.json`（如果有）和 `Content/` 复制到可执行文件旁
- 链接 `LimeRuntime`，并把引擎的 `LaunchMain.cpp` 编进这个可执行文件

> **为什么项目源码直接编进 exe，而不是先做成静态库？**
> 这是必须的，不是风格问题。Pass 和 Panel 靠静态初始化器自注册，如果放进静态库，链接器会认为「这个 .obj 里没有被引用的符号」从而整个丢弃，注册就静默失效了。

### 只写一个 JSON 的项目

`CMakeLists.txt` 也可以省掉：**只要目录里有 `ProjectSettings.json`，项目就会被加入构建**，所需的 CMake 胶水代码由构建系统生成到 `Intermediate/Generated/`（已在 `.gitignore` 中，不污染源码树）。

仓库里的 `Projects/GltfViewer/` 就是这样：整个项目只有一个 `ProjectSettings.json`，它加载并渲染一个 glTF 模型 —— 因为绘制场景的 Pass 和着色器都是引擎内置的。

需要写 Pass 或 Panel 时再补上 `CMakeLists.txt` 即可，两种形式没有其他差别。

## 第二步：ProjectSettings.json

```json
{
	"version": 1,
	"name": "MyGame",
	"window": {
		"title": "MyGame",
		"width": 1600,
		"height": 900
	},
	"rhi": {
		"backend": "d3d12",
		"vsync": true,
		"backBufferCount": 3,
		"validation": "debugOnly"
	},
	"editor": {
		"enabled": true
	},
	"automation": {
		"enabled": true,
		"port": 5613
	}
}
```

CMake 在配置阶段也读这个文件，所以构建期和运行期的项目名不可能对不上。

### 各键说明

| 键 | 取值 | 说明 |
| --- | --- | --- |
| `name` | 字符串 | 可执行文件名与 Shader 输出目录名。**不可在运行时修改** |
| `window.title` | 字符串 | 窗口标题，是唯一能即时生效的窗口设置 |
| `window.width` / `height` | 1..16384 | 上限对应 `FViewportTarget::MaxSize` |
| `rhi.backend` | `d3d12` \| `vulkan` | 设备创建时固定 |
| `rhi.vsync` | 布尔 | |
| `rhi.backBufferCount` | 2..4 | |
| `rhi.validation` | `off` \| `debugOnly` \| `on` | `debugOnly` 表示仅 Debug 构建开启 |
| `editor.enabled` | 布尔 | 关闭后场景直接渲染到交换链，不创建离屏目标 |
| `automation.enabled` | 布尔 | 自动化 HTTP 服务 |
| `automation.port` | 0..65535 | `0` 表示由操作系统分配，用于多实例并行 |

> **全部设置一律重启后生效，不支持热更新。**
>
> 这些值在启动时读一次（创建窗口和设备的时候），之后引擎不再读取。所以编辑器里的 `Project Settings` 面板本质上是个 **JSON 编辑器** —— 它编辑的是下次启动的配置，改完要点保存，然后重启。
>
> 这样设计的收益是：**运行中的配置不可变**，因此任何读取它的地方（面板、`settings.get`、Stats 面板）报告的都是引擎真正在用的值，而不会出现「请求了但没生效」的中间状态。

## EditorSettings.json（可选）

编辑器外观单独放一个文件，和 `ProjectSettings.json` 平级：

```json
{
	"version": 1,
	"appearance": {
		"fontSize": 16,
		"theme": "dark",
		"accentColor": [0.56, 0.83, 0.35]
	}
}
```

| 键 | 取值 | 说明 |
| --- | --- | --- |
| `appearance.fontSize` | 8..48 | 界面字号。超出范围会告警并退回默认值 16 |
| `appearance.theme` | `dark` / `light` / `classic` | 基础配色。`dark` 是编辑器实际调过的那套 |
| `appearance.accentColor` | 3 个 0..1 的数 | 强调色，作用于勾选框、滑块、选中的 Tab |

**这个文件是可选的。** 不写就用内置默认值，所以新建项目不需要专门创建它。

**为什么和 `ProjectSettings.json` 分开**：这些值只有编辑器读，运行时完全用不到。关掉 `LIME_BUILD_EDITOR` 的构建不该携带一份永远不会被应用的配置。同理，`FEditorSettings` 放在 `Engine/Source/Editor/` 而不是 `Runtime/Engine/`。

> **同样是重启后生效。**
>
> 字号必须如此 —— 它在启动时烘焙进字体图集，这也是用 `FontSizeBase` 而不是 `FontScaleMain` 的原因：后者是把图集放大，字会糊。颜色理论上可以即时生效，但让三个值遵守同一条规则，界面显示的内容才始终和文件一致。
>
> 编辑器里的 `Editor Settings` 面板默认不显示，从 `Window` 菜单打开。它和 `Project Settings` 面板行为一致：保存写回**源码树**里的 `Projects/<项目名>/EditorSettings.json`，同时刷新可执行文件旁的副本，采用「读-改-写」以保留注释和未知键。

## 第三步：源文件（可选）

`Source/` 可以为空，甚至可以不存在 —— 项目会正常构建，只是没有自己的 Pass 和 Panel，渲染完全由引擎内置的部分完成。

如果只想加载一个 glTF 模型看看，这就够了：在 `ProjectSettings.json` 里加一个 `scene` 分组即可，见 [06-场景与资产.md](06-场景与资产.md)。

要写自己的渲染，照 [02-自定义Pass.md](02-自定义Pass.md) 写第一个 Pass。下面是一个不做任何渲染的最小骨架：

```cpp
// Source/EmptyPass.cpp
#include "Renderer/RenderPassRegistry.h"

namespace MyGame
{
	class FEmptyPass final : public Lime::TRenderPass<FEmptyPass>
	{
	public:
		static constexpr Lime::ERenderPassPriority Priority = Lime::ERenderPassPriority::Scene;

		const char* GetName() const override { return "Empty"; }

		bool Initialize(Lime::FRenderer& Renderer) override
		{
			LIME_UNUSED(Renderer);
			return true;
		}
		void Shutdown() override {}
		void Render(const Lime::FFrameContext& Context) override { LIME_UNUSED(Context); }
	};
} // namespace MyGame

LIME_REGISTER_RENDER_PASS(MyGame::FEmptyPass);
```

## 第四步：构建运行

```powershell
./Scripts/Build.ps1
./Projects/MyGame/Binaries/Debug/MyGame.exe
```

CMake 会打印一行确认：

```
-- Project MyGame: D:/LimeEngine/Projects/MyGame/Source -> D:/LimeEngine/Projects/MyGame/Binaries/<Config>
```

## 命令行覆盖

配置文件是默认值，命令行优先。切换后端不需要改文件：

```powershell
MyGame.exe --rhi=vulkan
MyGame.exe --rhi=d3d12
MyGame.exe --no-editor              # 仅运行时，无编辑器 UI
MyGame.exe --width=1280 --height=720
MyGame.exe --no-vsync
MyGame.exe --validation=off         # 还可以是 debugOnly、on
MyGame.exe --project=<某个 ProjectSettings.json 的路径>
MyGame.exe --automation-port=0      # 开启自动化，端口由系统分配
MyGame.exe --no-automation
```

## 启动顺序

了解这个顺序，就知道自己的代码在什么时机被调用：

```
1. 读 ProjectSettings.json，应用命令行覆盖
2. 创建窗口（同时安装输入回调，必须早于编辑器初始化）
3. 创建 RHI 设备与交换链
4. 初始化 Renderer 与 ShaderLibrary
5. 初始化 Editor，实例化全部注册的 Panel
6. 实例化全部注册的 Pass，按 Priority 排序 —— 你的 Initialize 在这里
7. 加载 scene.gltf 配置的场景，并摆好相机
8. 启动自动化服务（若开启）
9. 进入主循环
```

第 6 步在设备就绪之后，所以 Pass 的 `Initialize` 里可以放心创建 GPU 资源。

第 2 步的顺序是**正确性前提**：ImGui 的 GLFW 后端安装的是链式回调（保存已有回调并在自己处理后转发），所以窗口必须先装好自己的回调。反过来的话 ImGui 会覆盖掉引擎的回调，键鼠输入就只有一套能用。

## 构建输出位置

**每个项目的产物都放在项目自身目录下**，不进共用的 `Build` 树。运行时产生的文件也都在里面：

```
Projects/MyGame/
  Source/ Shaders/ Content/ Automation/   ← 手写的内容，纳入 git
  ProjectSettings.json
  EditorSettings.json           可选
  Binaries/Debug/               ← 这个项目的全部产物，也是它的工作目录
    MyGame.exe
    ProjectSettings.json        构建时复制的副本
    EditorSettings.json         同上
    Shaders/Engine/             引擎 Shader（从 staging 复制进来）
    Shaders/MyGame/             项目 Shader（直接编译到这里）
    Content/                    引擎资产
    Content/MyGame/             项目资产
    Saved/
      Logs/LimeEngine.log
      EditorLayout.ini          停靠布局
      Screenshots/
      Automation/<pid>.json     自动化端点
    AutomationEndpoint.json
  Intermediate/                 ← 中间产物，可随时删除
    Build/                      CMakeFiles、.obj、Ninja 片段
    Lib/Debug/                  导入库与编译器 pdb

Build/ninja/                    ← 只放引擎级产物
  Bin/Debug/LimeTests.exe       工具类可执行文件
  Bin/Debug/ShaderMake.exe
  Staging/Debug/Shaders/Engine/ 引擎 Shader，只编译一次
  Lib/Debug/                    引擎静态库
```

`Binaries/` 和 `Intermediate/` 都在 `.gitignore` 里，所以项目目录可以整体拷走而不带上构建状态。

**为什么每个项目要独占目录**：引擎的 `Shaders/`、`Content/`、`Saved/`、`ProjectSettings.json` 全部相对可执行文件解析。如果多个项目共用一个目录，各自的 `ProjectSettings.json` 会互相覆盖 —— 后构建的那个会让先构建的项目读到错误的项目名，进而去错误的路径找 Shader，导致 Pass 初始化失败。

引擎 Shader 只编译一次，输出到 `Build/ninja/Staging/<Config>/Shaders/Engine`，再复制进各个项目的 `Binaries/<Config>/Shaders/Engine`。所以增加项目不会让 Shader 编译时间翻倍。

`Shaders/` 下每个「所有者」占一个子目录，后端目录在其内部：

```
Shaders/Engine/DXIL/ImGui/ImGui_MainVS.dxil
Shaders/Engine/SPIRV/ImGui/ImGui_MainVS.spirv
Shaders/MyGame/DXIL/Triangle/Triangle_MainVS.dxil
```

引擎 Shader 单独占 `Engine/` 而不是铺在 `Shaders/` 根下，是为了让它和项目 Shader 完全对称 —— 两者走同一套搜索根机制，而且叫 `Engine` 的项目不会和内置 Shader 撞名。

`Saved/` 已在 `.gitignore` 中。

编辑器里点「保存」写回的是**源码树**里的 `Projects/MyGame/ProjectSettings.json`，同时刷新可执行文件旁的副本 —— 所以改动不会在下次构建时被覆盖丢失。写入是「读-改-写」，注释、键顺序、引擎不认识的键都会保留。
