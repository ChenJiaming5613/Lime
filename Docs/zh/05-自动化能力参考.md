# 自动化能力参考

全部命令、HTTP 协议、Python API 速查。使用方法见 [04-自动化脚本.md](04-自动化脚本.md)。

## 开关与端口

Debug 构建默认开启。`LIME_BUILD_AUTOMATION=OFF` 会把整个模块从二进制中移除（不是运行时禁用 —— 编出来的 exe 里连 httplib 的字符串都不存在）。

```json
"automation": { "enabled": true, "port": 5613 }
```

```powershell
MyGame.exe                          # 用配置文件里的端口，默认 5613
MyGame.exe --automation-port=9000   # 指定端口，同时隐含开启
MyGame.exe --automation-port=0      # 由系统分配，用于多实例并行
MyGame.exe --no-automation          # 关闭
```

服务只绑定 `127.0.0.1`，因为这些命令能读写引擎的全部状态。

## 端点发现

引擎启动后写两个文件，脚本靠它们找到端口，不需要事先约定：

| 文件 | 位置 | 用途 |
| --- | --- | --- |
| `AutomationEndpoint.json` | 项目目录下 | 最近一个实例，方便手工查看 |
| `Saved/Automation/<pid>.json` | 项目目录下 | 每进程一份，多实例并行时用它 |

「项目目录」指 `Projects/<项目名>/Binaries/<Config>/`，每个项目独占一个。`discover_engines()` 会遍历全部项目目录，所以能同时发现不同项目的实例。

```json
{
  "port": 5613,
  "url": "http://127.0.0.1:5613",
  "protocol": 1,
  "project": "HelloTriangle",
  "pid": 52056
}
```

正常退出时会删除属于自己的那份（按 pid 校验，不会删掉别的实例的）。`discover_engines()` 还会逐个探测，所以崩溃残留的文件会被过滤掉。

## HTTP 协议

JSON over HTTP/1.1，任何有 HTTP 客户端的语言都能驱动。

| 方法与路径 | 请求体 | 响应 |
| --- | --- | --- |
| `POST /command` | `{"command": "...", "params": {...}}` | `{"ok": true, "result": {...}}` |
| `POST /command/<名字>` | `{...params...}`，可为空 | 同上，命令名取自路径 |
| `POST /batch` | `[{"command": ...}, ...]` | `{"ok": true, "replies": [...]}` 按序一一对应 |
| `GET /` | — | 服务标识、协议版本、当前帧 |
| `GET /commands` | — | 命令清单 |
| `GET /screenshot?source=viewport` | — | `image/png` 字节流 |

```powershell
curl -X POST http://127.0.0.1:5613/command/engine.info
curl -X POST http://127.0.0.1:5613/command -H "Content-Type: application/json" `
     -d '{"command":"pass.set","params":{"pass":"Quad","values":{"Scale":2.0}}}'
curl -o shot.png "http://127.0.0.1:5613/screenshot?source=viewport"
```

### 状态码语义

| 情况 | 状态码 | 说明 |
| --- | --- | --- |
| 命令被拒绝 | `200` + `ok=false` | 请求本身格式正确，是业务层面的失败 |
| 主线程超时 | `200` + `ok=false` | 消息为 `Timed out waiting for the main thread`，默认 30 秒 |
| 请求体不是合法 JSON | `400` | |
| `source` 参数非法 | `400` | |
| 路径不存在 | `404` | 响应体仍是 JSON |

区分的依据是「请求是否well-formed」：格式没问题但引擎做不到，用 `200` + `ok=false`；请求本身有毛病，用 `4xx`。

批量执行中某条失败**不影响前后**，每条都有独立的 `ok`：

```json
{"ok": true, "replies": [
  {"ok": true, "result": {...}},
  {"ok": false, "error": "Unknown command 'nope'; GET /commands for the list"},
  {"ok": true, "result": {...}}
]}
```

### 渲染 Pass

| 命令 | 参数 | 返回 |
| --- | --- | --- |
| `pass.list` | — | `passes`：`name`、`priority`、`hasSettings` |
| `pass.describe` | `pass` | `fields`：每个字段的完整元数据 |
| `pass.get` | `pass` | `values`：字段名到值 |
| `pass.set` | `pass`、`values` | `applied`：写成功的字段名；`values`：写后全部值 |

`pass.list` 按执行顺序返回：

```json
{"passes": [
  {"name": "Triangle", "priority": 0, "hasSettings": true},
  {"name": "ImGui", "priority": 3000, "hasSettings": false}
]}
```

**`pass` 参数用的是 `GetName()` 返回的名字**（如 `"Triangle"`），不是 C++ 类名。

`pass.describe` 是这套机制的关键 —— 它让脚本可以**发现**合法取值，而不是硬编码：

```json
{"pass": "Triangle", "fields": [
  {"name": "bPaused", "type": "bool", "value": false,
   "displayName": "Pause rotation", "widget": "automatic",
   "readOnly": false, "transient": false},
  {"name": "RotationSpeed", "type": "float", "value": 1.0,
   "displayName": "Speed", "tooltip": "Radians per second",
   "min": -6.0, "max": 6.0, "widget": "slider",
   "readOnly": false, "transient": false},
  {"name": "Tint", "type": "vector4", "value": [1.0, 1.0, 1.0, 1.0],
   "displayName": "Tint", "widget": "color",
   "readOnly": false, "transient": false}
]}
```

| 字段 | 说明 |
| --- | --- |
| `name` | **C++ 变量名**，`pass.set` 用它 |
| `type` | `bool` \| `float` \| `int32` \| `uint32` \| `vector2` \| `vector3` \| `vector4` |
| `value` | 当前值，向量是数组 |
| `displayName` | Inspector 里的标签，**不能用于 `pass.set`** |
| `tooltip` | 有 `.Tooltip()` 时出现 |
| `min` / `max` | 有 `.Range()` 时出现 |
| `widget` | `automatic` \| `slider` \| `drag` \| `color` \| `checkbox` |
| `readOnly` | `.ReadOnly()` 标记的字段，写入会被拒绝 |
| `transient` | `.Transient()` 标记的字段，不存盘但可读写 |

`pass.set` 的拒绝情形，错误消息都会点明字段名：

| 情形 | 错误消息 |
| --- | --- |
| 字段不存在 | `Unknown field 'xxx'` |
| 类型不匹配 | `... does not fit ...` |
| 字段是只读 | `... is read only` |
| 向量长度不对 | 不会逐分量部分写入 |

> **`pass.set` 不是原子的。** 字段按顺序逐个写入，中途失败前面的已经生效了。错误消息会带上写入了几个，例如
> `Unknown field 'Nope' (applied 1 field(s) before failing)`。
> 需要确定的状态，就把这次调用当作「可能部分生效」，随后用 `pass.get` 确认。
> 顺序不保证，所以不要依赖「哪一个先写」。

### 场景

| 命令 | 参数 | 返回 |
| --- | --- | --- |
| `scene.info` | — | `loading`、`load`、`loaded`、`path`、`entities`、`meshEntities`、`triangles`、`materials`、`textures`、`roots` |
| `scene.list` | — | `roots`：层级树，子节点嵌套在 `children` 里 |
| `scene.camera.get` | — | `position`、`forward`、`aspectRatio`、`nearPlane`、`farPlane`、`projection` |
| `scene.camera.set` | `position`、`yaw`、`pitch` | `position`、`forward`：实际生效的值 |
| `scene.select` | `name`（省略则清除） | `selected`、`id` |

`scene.info` 在没有场景时返回 `loaded: false` 而不是失败 —— 「是否加载了场景」是个合理的问题，而没有场景的项目是合法配置。

```json
{"loading": false, "load": {"loading": false, "elapsedSeconds": 0.0, "file": "DamagedHelmet.glb",
                            "phase": "Done", "texturesDone": 5, "textureCount": 5,
                            "meshesDone": 1, "meshCount": 1},
 "loaded": true, "path": "D:/.../DamagedHelmet.glb",
 "entities": 2, "meshEntities": 1, "triangles": 15452,
 "materials": 1, "textures": 5, "roots": 2}
```

glTF 在后台线程导入，所以启动后场景不是立刻就绪：大场景可以在窗口已经可以操作时仍在解析。`loading` 就是为此存在的 —— 脚本据此等待，而不是猜一个 sleep 时长。这也是 `loaded: false` 的两种含义的区分方式：正在后台加载，还是这个项目本来没有配置场景。

```python
# 等到场景真正就绪，在慢机器上同样可靠
while engine.call("scene.info")["loading"]:
    engine.wait_frames(5)
```

`load` 里还有 `phase`（`Parsing` / `Textures` / `Meshes` / `Finishing` / `Done`）与两组计数，用于报告进度；编辑器视口的加载提示读的就是同一份数据。计数在阶段结束后仍然保留，所以脚本可以在加载完成后断言贴图是否全部处理过。

解析阶段没有计数可报 —— tinygltf 是单次调用，返回时才结束。这不是省略，而是它的接口如此。

`scene.camera.set` 的三个参数都可以省略，未给出的字段保持当前值 —— 这让「移到这里」和「转到这个角度」各自是一行调用。返回值是**实际生效的**位姿，与请求可能不同：俯仰会被夹在 ±89°。

这条命令是让截图可复现的前提：

```python
engine.call("scene.camera.set", position=[0.0, 0.0, -4.0], yaw=0.0, pitch=0.0)
engine.wait_frames(5)
first = engine.screenshot(source="viewport")

engine.wait_frames(5)
assert engine.screenshot(source="viewport") == first
```

> 等待帧数要给够。改设置在下一帧生效，截图本身也要等一帧渲染完成，等太少会取到改动落地前的画面而误判为「没变化」。

`scene.select` 只在编辑器启用时可用。名称来自 `scene.list`，glTF 的节点名不唯一，重名时取第一个匹配。

场景的完整说明见 [06-场景与资产.md](06-场景与资产.md)。

### 项目设置

**设置一律重启后生效**，所以这三条命令区分两件事：**正在运行的配置**（不可变）和**待保存的草稿**（可编辑）。

| 命令 | 参数 | 返回 |
| --- | --- | --- |
| `settings.get` | — | `settings`：运行中的配置；`pending`：草稿；`dirty`：两者是否不同 |
| `settings.set` | `settings`：部分对象 | `pending`：编辑后的草稿；`restartRequired`：恒为 `true` |
| `settings.save` | — | `saved`：把草稿写回源码树的 `ProjectSettings.json` |

`settings.get` 返回的 `settings` 是**引擎真正在用的值**，命令行覆盖也算在内。例如用 `--width=1024` 启动，即使文件里写的是 1600，这里也返回 1024。

```json
{
  "settings": {"window": {"title": "LimeEngine - HelloTriangle", "width": 1024, ...}, ...},
  "pending":  {"window": {"title": "LimeEngine - HelloTriangle", "width": 1024, ...}, ...},
  "dirty": false
}
```

`settings.set` 接受**部分对象**，未提及的键保持不变。它只改草稿，**不影响运行中的会话**：

```python
e.set_settings({'window': {'title': 'Edited', 'width': 1920}})
e.get_settings()['window']['width']          # 仍是 1024，运行中的值没变
e.get_pending_settings()['window']['width']  # 1920，草稿记录了编辑
e.has_unsaved_settings()                     # True
e.save_settings()                            # 写回文件，下次启动生效
```

**校验是原子的** —— 请求里有任何一个非法值，整个请求都会被拒绝，草稿不会被部分更新：

```json
// 这个请求会整体失败，width 也不会进入草稿
{"settings": {"window": {"width": 1024}, "rhi": {"backBufferCount": 99}}}
```

`settings.save` 写回源码树，并刷新可执行文件旁的副本；写入是「读-改-写」，注释、键顺序、引擎不认识的键都保留。

### UI 测试

| 命令 | 参数 | 返回 |
| --- | --- | --- |
| `uitest.list` | — | `tests`：`category`、`name`、`qualifiedName`、`status`、`durationSeconds` |
| `uitest.run` | `filter`（`Category/Name` 的子串，省略即全部） | `run`、`running`、`tested`、`succeeded`、`remaining` |
| `uitest.status` | — | 同上，另加 `tests` 逐条结果 |
| `uitest.abort` | — | 同 `uitest.run` 的字段 |

这套命令驱动 [Dear ImGui Test Engine](https://github.com/ocornut/imgui_test_engine)，**按控件路径定位并注入真实输入事件**，因此测试里不出现任何屏幕坐标。

和 `panel.show` 的区别是本质性的：后者直接改可见性标志，而 UI 测试会真的去点 Window 菜单里那一项、真的去拖那个滑块。所以它能抓到「菜单项接错了面板」「滑块的值没传到 Pass」这类前者永远发现不了的缺陷。

**`uitest.run` 是异步的**：排队后立即返回，由客户端轮询 `uitest.status`。一次 UI 测试要跨几十上百帧，而命令在主线程帧与帧之间执行 —— 如果在 handler 里等测试跑完，就会停住测试赖以推进的帧循环，那是死锁而不是「慢一点」。

`filter` 匹配不到任何测试会**报错**而非空跑，否则一个拼写错误看起来会和「全部通过」一模一样。

`run` 是单调递增的运行序号，用来区分「上一次运行已结束」和「本次还没开始」—— 轮询模式下这是避免竞态误判的关键。

```python
status = engine.run_ui_tests()                          # 全部
status = engine.run_ui_tests(filter="HelloTriangle")    # 或子集
assert not engine.failed_ui_tests(status)
```

`run_ui_tests()` 封装了轮询循环，它的 `timeout` 与单条命令的超时相互独立：单次轮询很快，但整轮运行可以远超任何单条命令允许的时长。

> 注意 `tested` / `succeeded` 统计的是**全部已注册测试**的当前状态，不只是本次运行的那些 —— 每个测试保留它最近一次参与运行的结果。要判断某个具体测试，请查 `tests` 里的 `qualifiedName`。

关掉 `LIME_BUILD_IMGUI_TEST_ENGINE` 后这四条命令不会注册，也不出现在 `GET /commands` 目录里。

## Python API

`Programs/lime_automation` 是独立包，**只用标准库**，裸 checkout 即可运行。pytest 套件（位于 `Tests/Python/`）另需 `Programs/lime_automation/requirements.txt`。

### LimeClient

```python
from lime_automation import LimeClient

engine = LimeClient()                          # 默认 http://127.0.0.1:5613
engine = LimeClient("http://127.0.0.1:9000")
```

| `capture_output` | `False` | 捕获子进程 stdout/stderr |
| `extra_args` | — | 追加命令行参数 |

诊断方法：`log_tail(lines)` 取引擎日志末尾（启动失败时自动附在异常里），`log_issues(level)` 取格式化的警告及以上条目。

### 发现已运行的引擎

```python
from lime_automation import find_engine, discover_engines

endpoint = find_engine(project="MyGame")     # 找不到抛 EngineNotFoundError
engine = endpoint.connect()

for item in discover_engines():              # 按时间倒序，已逐个探测存活
    print(item.url, item.pid, item.project)
```

### 异常

| 异常 | 含义 |
| --- | --- |
| `LimeAutomationError` | 基类 |
| `TransportError` | 连接失败、超时、被关闭 —— 引擎大概已经没了，应该终止 |
| `CommandError` | 引擎返回 `ok=false`，带 `command`、`message`、`params` |
| `EngineNotFoundError` | 找不到运行中的引擎 |
| `LaunchError` | 进程启不来或提前退出 |

区分前两者是有意义的：`TransportError` 意味着该停止整轮运行，而 `CommandError` 往往就是断言本身。

### 环境变量

| 变量 | 作用 |
| --- | --- |
| `LIME_ROOT` | 仓库根目录，向上查找失败时用 |
| `LIME_BUILD_DIR` | 存放可执行文件的 CMake 构建目录，ctest 集成用它 |

## 扩展命令

项目可以注册自己的命令，写法与引擎内置的一致：

```cpp
#include "Automation/AutomationCommandRegistry.h"

LIME_REGISTER_AUTOMATION_COMMAND("game.reset", "把场景恢复到初始状态",
                                 [](Lime::FAutomationInvocation& Invocation)
                                 {
	                                 // 在主线程的帧间执行，可以安全访问引擎状态
	                                 Invocation.GetResult()["reset"] = true;
                                 });
```

同名注册会覆盖，所以也可以替换内置命令。

从 Python 调用不需要改客户端库 —— `call` 是通用的：

```python
engine.call("game.reset")
```

## 命令行工具

```powershell
./Scripts/Automation.ps1 test                          # pytest 套件
./Scripts/Automation.ps1 test -Backend d3d12,vulkan    # 双后端矩阵
./Scripts/Automation.ps1 list                          # 列出项目脚本
./Scripts/Automation.ps1 info                          # 描述运行中的引擎
./Scripts/Automation.ps1 info -Port 5613               # 只看指定端口那个
./Scripts/Automation.ps1 run <脚本>                     # 起引擎跑脚本
./Scripts/Automation.ps1 run <脚本> -Attach             # 用已在跑的引擎
./Scripts/Automation.ps1 shell -Attach                 # 交互式 REPL

./Programs/lime_automation/shell.ps1                   # shell 一键入口
./Programs/lime_automation/shell.ps1 -Port 5613
```

`-Project`、`-Config`、`-Backend` 通用；`-Attach` 与 `-Port` 用于连接已在运行的引擎。

> PowerShell 会先解析以 `-` 开头的 token，所以**不要直接敲 `--attach`** —— 它会被 PowerShell 拦下报 `ParserError`，Python 根本收不到。用上面的 `-Attach` / `-Port`。

也可以直接用模块（需要 `Programs` 在 `PYTHONPATH` 里，两个 ps1 会自动设置）：

```powershell
$env:PYTHONPATH = "$PWD\Programs"
python -m lime_automation list --project MyGame
python -m lime_automation run quad --attach
python -m lime_automation info --port 5613

cd Tests/Python
python -m pytest -q --backend vulkan
```
